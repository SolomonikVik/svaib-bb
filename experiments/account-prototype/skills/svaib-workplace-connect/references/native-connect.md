# Штатное подключение

## Перед изменением

Определи точный executable, версию, config root/profile, cwd и источник MCP: установленный плагин или runtime-конфигурация BB. Для этого доступны публичные настройки/статус BB и штатные команды выбранного CLI. Сверь их с выбранными host/environment/provider; первый binary из PATH может быть другим клиентом. Не считай соседний CLI эквивалентом bundled SDK/CLI провайдера BB.

Отличи отсутствие установки от отключённого MCP, пользовательской policy, необходимости входа и старой сессии. Наличие CLI, списка tools и вход в модель не доказывают работу MCP. Уже установленный плагин не переустанавливай и не обновляй попутно. Пользовательскую policy и отключение сервера не обходи; вторую manual MCP entry для обхода ограничения не создавай.

Конфиги читай только по необходимым несекретным полям. Auth cache, secret settings, токены и полный environment не нужны: ими владеет штатный клиент. Не выводи конфиги целиком.

## Установка методологического плагина

BB-плагин уже содержит два проверенных методологических пакета: для Codex и Claude Code. Их доставляет тот же публичный Git-источник `https://github.com/SolomonikVik/svaib-bb`. Дополнительный репозиторий, архив, пользовательский Локальный JSON для обычной установки не нужен.

Через `bb plugin list --json` найди установленный `svaib-workplace`, его `rootDir`, версию и источник. Не бери путь из сообщения человека. Через `bb status --json` получи `dataDir` этого же локального BB. Сверь текущие host/environment/provider. При удалённой среде или неподтверждённом соответствии путей остановись с конкретной причиной, не копируй в случайный профиль.

Выбери методологический пакет только по фактическому провайдеру: `codex` → `codex`, `claude-code` → `claude`, `acp-claude-kimi` → `claude`. Это выбор method host; реальный provider ID, модель и профиль разговора сохраняются. Для Kimi (CC) проверь launcher из записи ACP-агента и его `CLAUDE_CONFIG_DIR`. У штатного настройщика профиль — `~/.bb/providers/kimi-cc/claude/`, CLI запускается как `node <абсолютный launch.mjs> --claude <аргументы>`. Установку плагина, MCP и OAuth выполняй этим CLI в том же профиле; глобальный `claude` не является его заменой. Для уже существующей обёртки сначала установи её фактический executable/config root, не создавай новый профиль молча. Обоим нельзя ставить один вариант хуков. Выполни `scripts/prepare_methods.py` из проверенного `rootDir`, передав `--provider` и `--data-dir` отдельными argv. Команду исполняешь ты; человек не должен искать каталог или править файлы. Нужен Python 3 — тот же runtime, который используют поставляемые методологические обработчики.

Помощник проверяет контрольные суммы, имена пакетов, выбранный host и принадлежность существующей копии. Он возвращает `marketplaceRoot` в постоянном состоянии BB. Используй именно этот результат. Не привязывай native marketplace прямо к `rootDir`: при обновлении BB-плагина путь к его версии меняется. Отказ подготовки не обходи ручным копированием поверх чужих файлов.

Перед установкой прочитай штатный список marketplace выбранного CLI в выбранном config root/profile. Если `svaib` уже связан с другим источником, покажи различие и согласуй замену; не удаляй чужой источник молча. Если источник совпал и нужная версия уже установлена, сохрани установку. Поддержку команд проверяй через `--help` точного binary.

Для нового Codex выполни штатную `plugin marketplace add`, передав полученный `marketplaceRoot` отдельным аргументом, затем `plugin add svaib@svaib`. Для нового Claude Code — `plugin marketplace add` с тем же результатом для его варианта, затем `plugin install svaib@svaib`. Сверь фактически установленную версию и явный host в установленных обработчиках с подготовленным пакетом. В Codex после установки и каждого обновления вызови `svaib_codex_hooks`: он автоматически доверяет хукам установленного svaib@svaib. Не используй флаг обхода trust. Для других подтверждений CLI или BB следуй штатному интерфейсу.

### Обновление

Обновление BB доставляет новые исходные пакеты, но само не обновляет native установку. Когда пользователь поручил обновление или установка требует нового методологического выпуска, снова найди текущий `rootDir` и выполни помощник. Постоянный `marketplaceRoot` сохранится. Помощник не затирает изменённые вручную или посторонние файлы и не понижает версию молча.

Затем обнови native установку штатно в том же профиле. Для локального источника Codex повтори `plugin add svaib@svaib`: `plugin marketplace upgrade` предназначен для Git-источника и здесь не подходит. В Claude Code сначала `plugin marketplace update svaib`, затем `plugin update svaib@svaib`. Проверь итоговую версию и контрольные файлы. Обновление BB и методологического плагина — отдельные операции; не объявляй их одновременными или атомарными. После изменения пакета продолжи в штатном свежем разговоре, если текущий runtime ещё использует прежнюю версию.

## Продолжение после перерыва

Незавершённая настройка сохраняет разговор и рабочие подключения. Если вход в кабинет не завершён, а старая браузерная форма или код больше не подходят, предложи одно действие: открыть svaib в BB и нажать «Продолжить» у нужного шага. Откроется обычный запрос агенту; агент проверит сохранённые входы и возобновит только незавершённую сторону. Для отдельного входа кабинета доступна кнопка «Войти в svaib». Не проси его заново объяснять задачу, копировать callback или разлогиниваться.

Если инструкция backend сообщает, что новый вход кабинета уже открыт, проверяй тот же вход штатным инструментом начала/ожидания входа кабинета без `reopenBrowser` и повторного OAuth. После успеха продолжай с незавершённого шага. Технические сроки кодов и запросов не являются сроком всей настройки. После закрытия BB сначала проверь сохранённые входы; новый запрос нужен только незавершённой стороне. Старые code/state/PKCE не восстанавливай.

## MCP OAuth

Найди точный ключ сервера через штатные list/get/status выбранного CLI, с ограниченным безопасным выводом. Codex видит plugin-backed сервер по ключу из его конфигурации; в проверенном Claude ключ имел форму `plugin:<plugin-name>:<mcp-server-name>`. Не подставляй пример имени и не угадывай ключ svaib. Поддерживаемые аргументы проверь по help именно `mcp login`: флаг `--json` этой команды в Codex 0.164.0 не поддерживается. Не повторяй auth для исправного подключения.

Runtime-contributed MCP, который CLI не видит, не становится plugin-backed от добавления дубликата. Для такого случая сначала проверь, каким публичным способом провайдер BB получает конфигурацию и можно ли штатно подключить тот же источник. Если способ не подтверждён, сообщи ограничение; не меняй скрытые routes или чужие credentials.

Для локального BB с браузером на том же host используй browser login. В Docker-стенде браузер и клиент работают внутри одного контейнера; штатный `BROWSER` уже настроен. Пользователю остаётся подтвердить вход в открывшейся вкладке.

### Codex: управляемый приёмник

При необходимости входа в Codex 0.166.0 вызови `svaib_connect_native_start`: передай проверенные абсолютные `executable`, `configRoot` и точный `serverKey`. Не выбирай профиль по умолчанию наугад. Backend проверит текущие thread/environment/host/provider и сам создаст один persistent-терминал с поставленным вместе с BB-плагином helper. Путь helper, cwd и остальные параметры рабочего места backend берёт сам. Пользователю не нужно запускать команды.

Helper использует официальный `codex app-server` и `mcpServer/oauth/login` с `timeoutSecs=3600`. Это отдельный native-процесс того же профиля, а не живая provider-сессия BB. Он не делает модельных ходов, не читает credential-файлы и не выводит OAuth URL, коды или токены в терминал/модель. PKCE, обмен и хранение выполняет сам Codex. Уже работающий native grant сохраняется без нового входа.

После результата сразу используй `svaib_connect_wait` с возвращённым `terminalId`. При `pending` продолжай ждать тот же процесс. После «Продолжить» агент в открытом разговоре проверяет сохранённое состояние и вызывает штатное ожидание/продолжение принадлежащего подключению helper. Оно повторно открывает исходный запрос только если остаток ожидания покрывает окно формы; иначе сначала завершает прежний app-server через EOF, дожидается реального выхода, затем проверяет штатное состояние входа в новом процессе. Если прежний процесс не завершился, второй не запускается. Не используй `terminal restart`, не запускай второй OAuth вручную и не читай terminal output.

Exit0 означает только штатный native-вход. После `handedOff` доступ проверяет свежий разговор BB через настоящий native MCP whoami; успешный helper не заменяет эту проверку. Если helper/tool недоступен или версия/профиль не подтверждены, сообщи ограничение: прямой `codex mcp login` имеет отдельный пятиминутный срок приёмника и не является равнозначной заменой обещанному ожиданию.

### Claude Code

Запускай OAuth непосредственной командой persistent-терминала BB с argv без shell-интерполяции:

```sh
bb terminal create --thread <текущий-thread-id> --title 'Вход в svaib' -- <точный-executable> mcp login <точный-server-key>
```

Используй реальный ID из контекста; не передавай credentials в argv. Если выбранному профилю нужны config flags или переменные окружения — сохрани именно его scope штатным способом на целевом host. Не читай токены и не передавай весь environment агенту. Если это не удаётся доказать, не запускай команду в scope по умолчанию.

В remote/headless сначала подтверди маршрут возврата. `--no-browser` — отдельный ручной режим: в проверенном Codex он не поднимает callback listener, а ждёт полный адрес возврата через stdin. Страница браузера с `ERR_CONNECTION_REFUSED` в таком режиме не доказывает сбой сервера svaib. Не выбирай этот режим для локального пользователя, которому обещан только вход в браузере. Если браузерный запуск недоступен, сообщи ограничение, прежде чем предлагать ручной перенос ссылки или callback; эти данные пользователь вводит только в терминал, не в чат.

Терминал остаётся у пользователя в BB. Наблюдать можно через `bb terminal show <terminal-id> --json`: статус и exitCode не содержат scrollback. Они относятся к OAuth только при прямом запуске команды; `terminal restart` создаёт обычный shell, и его `running` ничего не говорит о входе. После запуска OAuth не читай `output`, `attach`, `wait --contains` или буфер при ошибке: там могут быть auth URL, code и state. Ссылки входа и callback остаются в браузере/терминале вне чата модели. CLI exit 0 означает завершение команды, а не проверку MCP в разговоре.

Persistent-терминал сохраняет процесс при завершении хода агента, но не продлевает встроенный срок браузерного входа CLI. Не подставляй `startup_timeout_sec` или `tool_timeout_sec` как срок ожидания OAuth и не придумывай флаг таймаута. При `pending` сохраняй тот же терминал и вход. Если процесс завершился без успеха, прежняя браузерная ссылка может вести на уже закрытый callback: не проси человека обновлять её или переносить callback в чат. Объясни, что нужно продолжить незавершённый вход. В едином подключении для этого есть кнопка «Продолжить» на странице svaib в BB; она сохраняет тот же разговор и уже работающий вход кабинета.

Нажатие «Продолжить» или явная просьба повторить вход разрешает повтор только незавершённого шага. Сначала проверь сохранённое подключение штатным способом: поздний успешный вход не нужно заменять. Если вход всё ещё нужен и прежний терминал уже завершён, создай новый persistent-терминал с той же проверенной непосредственной командой в том же профиле. Не используй `terminal restart`: он запускает shell. Не разлогинивай кабинет или MCP и не запускай второй процесс, пока прежний работает. Кабинет и native MCP имеют отдельные grants: повторяется только сторона, которая не завершилась.

Не запускай второй терминал, пока первый вход не завершён. При отмене закрой только созданный для этого входа терминал, без logout рабочего подключения. Ошибку/таймаут опиши без credential-диагностики; уже работающие кабинет/MCP сохраняются, повторяется только незавершённый шаг.

Если после штатного входа текущий разговор не видит MCP, сначала используй доступный инструмент автоматического продолжения. При его отсутствии подготовь новый разговор в той же среде и настоящую MCP-проверку. Для этого агент готовит запрос проверки для нового обычного разговора BB, сохраняя ссылку на исходный разговор и выбранную связку. Не перезапускай BB, не очищай контекст и не используй приватные API для reconnect.
