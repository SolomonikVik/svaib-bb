# Штатное подключение

## Перед изменением

Определи точный executable, версию, config root/profile, cwd и источник MCP: установленный плагин или runtime-конфигурация BB. Используй для этого публичные настройки и статус BB, а также штатные команды выбранного CLI. Сверь их с выбранными host/environment/provider; первый binary из PATH может быть другим клиентом. Не считай соседний CLI эквивалентом bundled SDK/CLI провайдера BB.

Выясни, отсутствует ли установка, отключён ли MCP, мешает ли пользовательская policy, нужен ли вход или сессия устарела. Наличие CLI и списка tools, а также вход в модель не доказывают работу MCP. Уже установленный плагин не переустанавливай и не обновляй попутно. Пользовательскую policy и отключение сервера не обходи; вторую manual MCP entry для обхода ограничения не создавай.

В конфигах читай только необходимые несекретные поля. Auth cache, secret settings, токены и полный environment не нужны: ими владеет штатный клиент. Не выводи конфиги целиком.

## Установка методологического плагина

### Windows: подготовка компьютера

До первого ответа модели BB-плагин проверяет компьютер, на котором выполняются команды: Python 3.10+ запуском файла, Git for Windows и Git Bash, Node.js 22+ и npm, CLI BB. Недостающее устанавливает общий код подготовки; для Node используется существующий установщик. Рабочие профили, входы и модель сохраняются. Путь Python передаётся всем харнесам через `SVAIB_PYTHON`, путь Bash — через `CLAUDE_CODE_GIT_BASH_PATH`. Обновлённый PATH дополняет прежний; собственное средство запуска `python3` позволяет запустить и прежнюю регистрацию хуков.

Прочитай состояние командой `bb svaib-workplace runtime status`. При отказе назови его причину. После устранения причины повтори `bb svaib-workplace runtime prepare --retry`; удалённый компьютер укажи через `--host <id>`. Переносимый Node включается только явно: `bb svaib-workplace runtime prepare --retry --portable-node`. Отмена, отказ системных прав и таймаут не запускают этот резерв автоматически. Человек подтверждает только недоступный агенту запрос Windows. Ограничения администратора не обходи.

Наличие команды, псевдоним WindowsApps, ответ WinGet или готовность модели не подтверждают запуск хуков. Проверь настоящее событие карты и проверку спецификации на изолированном примере. Для чтения проверь `bb status --json`, `bb thread show --self --json` и `bb plugin list`. Затем проверь согласованную запись канонического файла: штатный отказ со спецификацией должен сохраниться.

### Запуск хуков на Windows

При техническом отказе сначала прочитай безопасный фрагмент диагностики: команда хука, стадия, код завершения и stderr. Различай ошибку средства запуска, штатный JSON-отказ со спецификацией и ошибку самой пользовательской команды. Не выводи полный отладочный журнал, OAuth URL и секреты. Для ремонта используй общий код подготовки вне перехватываемой команды PowerShell; не требуй сначала запустить команду, которую блокирует сломанный хук. Кэш плагина и чужую регистрацию вручную не переписывай, хуки не отключай.

Git for Windows с Git Bash входит в подготовку. После неё Bash должен запускаться именно из окружения BB/CC, которое исполняет хуки. Повторяющееся предупреждение про git проверяй по его точному тексту: без нового события не объявляй его устранённым.

Для провайдера `pi` перейди к подразделу `Pi` ниже. Команды marketplace Codex/Claude к нему не относятся.

BB и методологический плагин Harness обновляются независимо; поддерживаются текущая и две предыдущие minor-линии каждого. Сначала проверь установленный `svaib@svaib` в выбранном профиле. Работающий пакет из официальной раздачи сохраняй независимо от версии внутри BB. Для отсутствующего пакета BB содержит общий комплект Codex/Claude Code в `methods/common`, доставленный из `https://github.com/SolomonikVik/svaib-bb`. Его manifest и схему проверяет помощник подготовки.

Через `bb plugin list --json` найди установленный `svaib-workplace`, его `rootDir`, версию и источник. Не бери путь из сообщения человека. Через `bb status --json` получи `dataDir` этого же локального BB. Сверь текущие host/environment/provider. Если среда удалённая или соответствие путей не подтверждено, остановись и назови конкретную причину. Не копируй пакет в случайный профиль.

Выбери целевой CLI и его профиль только по фактическому провайдеру: `codex` → `--provider codex`, `claude-code` → `--provider claude`, `acp-claude-kimi` → `--provider claude`. В schema2 обоим готовится один и тот же пакет с auto-хуками; реальный provider ID, модель и профиль разговора сохраняются. Для Kimi (CC) проверь launcher из записи ACP-агента и его `CLAUDE_CONFIG_DIR`. Путь профиля Kimi бери из launcher установленной карточки BB. CLI запускается как `node <абсолютный launch.mjs> --claude <аргументы>`. Установку плагина, MCP и OAuth выполняй этим CLI в том же профиле; глобальный `claude` не является его заменой. Если обёртка уже есть, сначала выясни её фактический executable/config root. Не создавай новый профиль молча. Выполни `scripts/prepare_methods.py` из проверенного `rootDir`, передав `--provider` и `--data-dir` отдельными argv. Выполни команду сам. Человек не должен искать каталог или править файлы. Нужен Python 3 — тот же runtime, который используют поставляемые методологические обработчики.

Помощник проверяет контрольные суммы, имена и версию пакета, соответствие host схеме и принадлежность существующей копии. Он возвращает `marketplaceRoot` выбранного CLI в постоянном состоянии BB; более новый подготовленный пакет сохраняется. Используй именно этот результат. Не привязывай native marketplace прямо к `rootDir`: при обновлении BB-плагина путь к его версии меняется. Отказ подготовки не обходи ручным копированием поверх чужих файлов.

Перед установкой прочитай штатный список marketplace выбранного CLI в выбранном config root/profile. Официальные источники — раздача `SolomonikVik/svaib-plugin` и подготовленный BB marketplace. Уже установленный официальный пакет сохраняй. Если источник другой, покажи различие и согласуй его замену. Поддержку команд проверяй через `--help` точного binary.

Для нового Codex выполни штатную `plugin marketplace add`, передав полученный `marketplaceRoot` отдельным аргументом, затем `plugin add svaib@svaib`. Для нового Claude Code — `plugin marketplace add` с результатом помощника для его профиля, затем `plugin install svaib@svaib`. Сверь установленную версию и host в обработчиках с подготовленным пакетом. schema2 требует `auto`, прежняя schema1 — явный host выбранного CLI. Не переписывай команды хуков при установке. В Codex после установки и каждого обновления вызови `svaib_codex_hooks`: он автоматически доверяет хукам установленного svaib@svaib. Не используй флаг обхода trust. Для других подтверждений CLI или BB следуй штатному интерфейсу.

### Обновление

Обновляй по поручению или когда для конкретного действия нужна отсутствующая возможность. Различие версий BB и Harness само по себе не требует обновления. Для Git-раздачи используй штатное обновление её marketplace. Для пакета из BB найди текущий `rootDir` и запусти помощник: он сохранит постоянный `marketplaceRoot` и более новую версию. Изменённые вручную или посторонние файлы помощник оставляет для отдельного разбора.

Затем штатно обнови native-установку в том же профиле. Для локального источника Codex повтори `plugin add svaib@svaib`: `plugin marketplace upgrade` предназначен для Git-источника и здесь не подходит. В Claude Code сначала `plugin marketplace update svaib`, затем `plugin update svaib@svaib`. Проверь итоговую версию и контрольные файлы. Обновление BB и методологического плагина — отдельные операции; не объявляй их одновременными или атомарными. После изменения пакета продолжи в штатном свежем разговоре, если текущий runtime ещё использует прежнюю версию.

### Pi

Сохрани фактический provider `pi`, модель, executable, `PI_CODING_AGENT_DIR` и cwd разговора. Адаптер проверялся на Pi 1.5.1; запуск Pi и модельный ответ также проверены на Pi 1.5.2. Нужны Node ≥22.19 и Python ≥3.10. Адаптер Pi опубликован в Harness 0.12.0 и включён в BB 0.6.0; Harness 0.11.1 Pi не содержит. Старый BB-комплект может штатно отказать из-за отсутствующего Pi payload. В этом случае обнови согласованный комплект; не применяй Claude-команды и не обходи проверку. Публикация не заменяет живой проверки пакета, хуков и входа в текущем разговоре.

Карточка Kimi сначала использует штатный Pi и его профиль. Отдельный runtime доступен как явный резерв; в нём глобальная команда `pi` может отсутствовать. Получи проверенный запуск через `bb plugin rpc call svaib-workplace kimiPiRuntime --json`; сверь возвращённый `hostId` с текущим host. При `profile=ready` используй `registration.command` и весь массив `registration.args` перед аргументами CLI; `registration.agentDir` должен совпадать с фактическим профилем разговора. Поле `mode` различает штатный `native` и резервный `managed`; оба используют native Pi. В штатном режиме профиль может быть стандартным `~/.pi/agent`, даже если переменная не задана. Сверяй фактический каталог, а не наличие переменной. Все установки, MCP-команды и persistent-терминалы запускай тем же argv. Рабочий каталог и профиль не переключай. Если RPC не вернул регистрацию или версия плагина устарела, проверь фактический запуск обычным способом. Путь к профилю не угадывай.

При установке, согласованном обновлении или восстановлении метода выполни `scripts/prepare_methods.py --provider pi --data-dir <проверенный dataDir> --node <абсолютный Node> --npm-cli <абсолютный npm/bin/npm-cli.js>` из установленного BB-плагина. Node и npm бери из фактической установки выбранного host; Node должен быть не ниже 22.19. Помощник проверяет оба `package.json`, версию, вход расширения, child policy, общие hooks и checksum. `marketplaceRoot` — отдельный неизменяемый каталог версии: старый `methods/pi` и исходники прежних версий сохраняются, даже если на них ссылается действующий runtime.

Для локального источника Pi не устанавливает зависимости автоматически. Помощник сам вызывает npm с `--install-links --ignore-scripts`, создаёт независимую копию в `pi-runtimes/`, сверяет все поставленные файлы и проверяет разрешение `pi-subagents@0.87.0` и его используемых экспортов из `delegation.ts`. Ссылка вместо копии или отсутствие зависимости — отказ, даже если npm завершился успешно. Рабочие копии и входы сохраняются; неудачная попытка не переключает указатель готового runtime. Повторный вызов проверяет готовую копию и возвращает тот же путь; повреждённую оставляет и собирает новую. Используй только возвращённый `packageRoot`, а не `marketplaceRoot` или самостоятельно выбранный `runtime-pi-*`.

Для новой установки выполни точным Pi CLI в том же профиле `pi install <packageRoot>`. При обновлении сначала прочитай только native-регистрацию svaib: её точный `source`, scope и все поля объекта. Работающий официальный Git/npm-пакет сохраняй. Для прежней локальной регистрации используй `scripts/replace-pi-registration.mjs` этого скилла, запущенный проверенным Node с отдельными argv: `--settings <абсолютный settings.json выбранного scope> --old-source <точная прежняя строка source> --package-root <возвращённый packageRoot>`. User scope — `settings.json` внутри проверенного `PI_CODING_AGENT_DIR`, project scope — `.pi/settings.json` внутри cwd. Не используй объединённый список пакетов вместо выбранного scope.

Помощник под совместимой со штатным Pi блокировкой заменяет только source одной регистрации, сохраняя все поля объекта, остальные пакеты и настройки. При совпадении source с packageRoot он ничего не пишет; `remove` после этого не нужен. Сохранённые относительные source считаются от каталога соответствующего settings.json. Неоднозначная или отдельная новая регистрация — отказ, не повод удалять одну наугад. Запись атомарна: отказ оставляет прежнее. После успеха перечитай регистрацию и проверь загрузку. Для отката запусти тот же помощник в том же scope с новым source как `--old-source` и прежним существующим локальным packageRoot как `--package-root`; фильтры сохранятся. Если параллельное изменение не позволяет найти точную регистрацию, остановись, не восстанавливай весь конфиг поверх чужой правки. Прежние каталоги и входы сохраняй.

Сверь, что осталась одна регистрация svaib, остальные пакеты, фильтры ресурсов и настройки сохранены. Не добавляй отдельно вторую копию `pi-subagents`: svaib регистрирует готовый исполнитель из своей зависимости. Для Git/npm источников зависимости готовит штатный Pi. Активная сессия продолжает использовать прежний пакет до перезагрузки; переключение профиля не означает успешной загрузки расширения.

Native extension регистрирует сервер `svaib` с direct exposure из `.mcp.json`. Для CLI OAuth дополнительно нужен тот же сервер в native `mcp.json`: сначала проверь ограниченные поля существующей записи; если её нет, выполни `pi mcp add svaib --url <url из проверенного .mcp.json> --exposure direct`. Не заменяй чужую запись и отключённую policy. Если имя и URL совпадают, это CLI-конфигурация того же сервера. Новый псевдоним создаст дубликат. Вход — точным `pi mcp login svaib --timeout 3600` в persistent-терминале BB с тем же профилем. Пользователь подтверждает браузерную форму; auth URL и callback в чат не переносятся. Сразу зарегистрируй терминал в `svaib_connect_wait` с точным serverKey и PI_CODING_AGENT_DIR как configRoot. BB сам продолжит разговор после завершения; «готово» от пользователя не требуется. Правила наблюдения статуса терминала ниже применяются и к Pi.

В Pi 1.5.2 параметр `--timeout 3600` ограничивает ожидание авторизации, но встроенный приёмник callback отдельно истекает через пять минут. До запуска проверь, что штатный browser launcher открывает браузер в том же сетевом окружении, что Pi; пользователь только подтверждает внешнюю форму. Объясни, что на подтверждение есть примерно пять минут. Создай один терминал в нужном разговоре; браузер должен открыть сам CLI через проверенный launcher. Открытие ссылки из терминала пользователем — только явно названный резерв при подтверждённой недоступности автоматического открытия, не основной путь. Для Pi в контейнере нужен браузер внутри контейнера или другой проверенный маршрут к его callback. Браузер на другом устройстве или хосте не обращается к `localhost` контейнера автоматически. Если подходящий маршрут недоступен, назови ограничение до входа. Не проси пересылать ссылку или callback в чат.

Если время истекло или вход прерван, спокойно объясни это человеку. Проверь статус прежнего терминала и сохранённого подключения, не читая вывод; второй вход не запускай, пока первый работает. Когда человек готов и вход всё ещё нужен, создай новый терминал той же командой в том же профиле с проверенным автоматическим открытием браузера и зарегистрируй ожидание. Старую ссылку не используй; модельный вход Kimi повторять не требуется.

Проверь запуск `pi/extension.ts`, отсутствие ошибок dependency/extension, карту и фактический гейт спецификации в изолированном файле. Подключение завершает настоящий вызов direct MCP `whoami` в текущем BB-разговоре. Статус CLI его не заменяет. Только если после установки/входа инструменты не появились, используй reload или один свежий разговор через общий flow BB, сохранив provider/model. Кабинет, явный выбор компании, постоянная папка и Screen идут по общему онбордингу. Автоматического доверия хукам Codex для Pi нет.

Модельный вход отделён от svaib. Для ключа Kimi Code достаточно ключа в native auth и `kimi-coding.baseUrl=https://api.kimi.ai/coding/v1` в выбранном `models.json`; карточка готовит их сама. Только для OAuth модели дополнительно нужен `KIMI_CODE_OAUTH_HOST=https://auth.kimi.ai`. Уже работающие ключи и OAuth/refresh сохраняй. Настройка или смена аккаунта модели не входит в подключение svaib; не запускай её повторно ради MCP. До первого ответа модели веди по справке `kimi-pi-bb.md`, сохраняя выбранный пользователем Pi.

## Продолжение после перерыва

Незавершённая настройка сохраняет разговор и рабочие подключения. Если вход в кабинет не завершён, а старая браузерная форма или код больше не подходят, предложи одно действие: открыть svaib в BB и нажать «Продолжить» у нужного шага. Откроется обычный запрос агенту; агент проверит сохранённые входы и возобновит только незавершённую сторону. Для отдельного входа кабинета доступна кнопка «Войти в svaib». Не проси его заново объяснять задачу, копировать callback или разлогиниваться.

Если инструкция backend сообщает, что новый вход в кабинет уже открыт, проверяй этот вход штатным инструментом начала/ожидания. Не используй `reopenBrowser` и не повторяй OAuth. После успеха продолжай с незавершённого шага. Сроки действия кодов и запросов не ограничивают срок всей настройки. После закрытия BB сначала проверь сохранённые входы; новый запрос нужен только незавершённой стороне. Старые code/state/PKCE не восстанавливай.

## MCP OAuth

Найди точный ключ сервера через штатные list/get/status выбранного CLI, с ограниченным безопасным выводом. Codex видит plugin-backed сервер по ключу из его конфигурации; в проверенном Claude ключ имел форму `plugin:<plugin-name>:<mcp-server-name>`. Не подставляй пример имени и не угадывай ключ svaib. Проверь поддерживаемые аргументы по help команды `mcp login`: в Codex 0.164.0 она не поддерживает флаг `--json`. Не повторяй auth для исправного подключения.

Runtime-contributed MCP, который CLI не видит, не становится plugin-backed от добавления дубликата. В этом случае сначала проверь, каким публичным способом провайдер BB получает конфигурацию и можно ли штатно подключить тот же источник. Если способ не подтверждён, сообщи ограничение; не меняй скрытые routes или чужие credentials.

Для локального BB с браузером на том же host используй browser login. В Docker-стенде браузер и клиент работают внутри одного контейнера; штатный `BROWSER` уже настроен. Пользователю остаётся подтвердить вход в открывшейся вкладке.

### Codex: управляемый приёмник

При необходимости входа в Codex вызови `svaib_connect_native_start`: передай проверенные абсолютные `executable`, `configRoot` и точный `serverKey`. Не выбирай профиль по умолчанию наугад. Backend проверит текущие thread/environment/host/provider и сам создаст один persistent-терминал с поставленным вместе с BB-плагином helper. Номер версии Codex не является условием запуска: helper проверяет фактический ответ нужного native API. Путь helper, cwd и остальные параметры рабочего места backend берёт сам. Пользователю не нужно запускать команды.

Helper использует официальный `codex app-server` и `mcpServer/oauth/login` с `timeoutSecs=3600`. Это отдельный native-процесс того же профиля, а не живая provider-сессия BB. Он не делает модельных ходов, не читает credential-файлы и не выводит OAuth URL, коды или токены в терминал/модель. PKCE, обмен и хранение выполняет сам Codex. Уже работающий native grant сохраняется без нового входа.

Получив результат, используй `svaib_connect_wait` с возвращённым `terminalId` и тем же `serverKey`. При `automatic:true` ожиданием владеет BB: он сам возобновит этот разговор, повторять инструмент и ждать сообщения «готово» не нужно. После «Продолжить» агент в открытом разговоре проверяет сохранённое состояние и вызывает штатное ожидание/продолжение принадлежащего подключению helper. Ожидание/продолжение повторно открывает исходный запрос, только если оставшегося времени ожидания хватает на срок действия формы. Иначе оно сначала завершает прежний app-server через EOF, дожидается реального выхода и затем проверяет штатное состояние входа в новом процессе. Если прежний процесс не завершился, второй не запускается. Не используй `terminal restart`, не запускай второй OAuth вручную и не читай terminal output.

Exit0 означает только штатный native-вход. После ожидания проверь здесь native MCP whoami. Если инструмента нет в текущей сессии, проверь штатное подключение MCP и обновление списка инструментов харнеса; отдельного verify-flow svaib нет. Успешный helper не заменяет настоящую MCP-проверку. Если нужный API helper недоступен, проверь `mcp login --help` фактического CLI и используй штатный вход в том же профиле. Объясни фактический срок ожидания: прямой `codex mcp login` на проверенном стенде имел отдельный пятиминутный срок приёмника и не равнозначен обещанному часовому ожиданию helper. Не требуй конкретной версии Codex ради совпадения со стендом. Неподтверждённый профиль сначала выясни, сохраняя работающие входы.

### Claude Code

Запускай OAuth непосредственной командой persistent-терминала BB с argv без shell-интерполяции:

```sh
bb terminal create --thread <текущий-thread-id> --title 'Вход в svaib' -- <точный-executable> mcp login <точный-server-key>
```

Используй реальный ID из контекста; не передавай credentials в argv. Если выбранному профилю нужны config flags или переменные окружения — сохрани именно его scope штатным способом на целевом host. Не читай токены и не передавай весь environment агенту. Если не удаётся подтвердить сохранение нужного scope, не запускай команду в scope по умолчанию.

В remote/headless сначала подтверди маршрут возврата. `--no-browser` — отдельный ручной режим: в проверенном Codex он не поднимает callback listener, а ждёт полный адрес возврата через stdin. Страница браузера с `ERR_CONNECTION_REFUSED` в таком режиме не доказывает сбой сервера svaib. Не выбирай этот режим для локального пользователя, которому обещан только вход в браузере. Если браузерный запуск недоступен, сообщи ограничение, прежде чем предлагать ручной перенос ссылки или callback; эти данные пользователь вводит только в терминал, не в чат.

Сразу после создания терминала зарегистрируй его через `svaib_connect_wait`: передай `terminalId`, проверенные `serverKey` и `configRoot`. Это работает и в обычном разговоре без START или входа кабинета. BB сам наблюдает состояние и продолжает разговор; не проси человека писать «готово». Для Kimi (CC) переподключение именно этого сервера выполняется отдельной точной slash-командой перед ходом проверки whoami.

Терминал остаётся у пользователя в BB. Проверять его состояние можно через `bb terminal show <terminal-id> --json`: статус и exitCode не содержат scrollback. Статус и exitCode относятся к OAuth только при прямом запуске команды. `terminal restart` создаёт обычный shell; его `running` ничего не говорит о входе. После запуска OAuth не читай `output`, `attach`, `wait --contains` или буфер при ошибке: там могут быть auth URL, code и state. Ссылки входа и callback остаются в браузере/терминале вне чата модели. CLI exit 0 подтверждает завершение команды, но не проверку MCP в разговоре.

Persistent-терминал сохраняет процесс при завершении хода агента, но не продлевает встроенный срок браузерного входа CLI. Не подставляй `startup_timeout_sec` или `tool_timeout_sec` как срок ожидания OAuth и не придумывай флаг таймаута. При `pending` сохраняй тот же терминал и вход. Если процесс завершился без успеха, прежняя браузерная ссылка может вести на уже закрытый callback: не проси человека обновлять её или переносить callback в чат. Объясни, что нужно продолжить незавершённый вход. В едином подключении для этого есть кнопка «Продолжить» на странице svaib в BB; она сохраняет тот же разговор и уже работающий вход кабинета.

Нажатие «Продолжить» или явная просьба повторить вход разрешает повтор только незавершённого шага. Сначала проверь сохранённое подключение штатным способом: поздний успешный вход не нужно заменять. Если вход всё ещё нужен и прежний терминал уже завершён, создай новый persistent-терминал с той же проверенной непосредственной командой в том же профиле. Не используй `terminal restart`: он запускает shell. Не разлогинивай кабинет или MCP и не запускай второй процесс, пока прежний работает. Кабинет и native MCP имеют отдельные grants: повторяется только сторона, которая не завершилась.

Не запускай второй терминал, пока первый вход не завершён. При отмене закрой только терминал, созданный для этого входа. Не выполняй logout рабочего подключения. Опиши ошибку/таймаут без credential-диагностики. Сохраняй уже работающие кабинет/MCP и повторяй только незавершённый шаг.

Если после штатного входа текущий разговор не видит MCP, сначала проверь штатное переподключение MCP и обновление списка инструментов харнеса. Не объявляй список инструментов неизменяемым без проверки. Если публичного способа обновления именно этого харнеса нет, явно назови ограничение; только тогда подготовь минимальное продолжение в той же среде с сохранением готового входа. Для этого агент готовит запрос проверки для нового обычного разговора BB, сохраняя ссылку на исходный разговор и выбранную связку. Не перезапускай BB, не очищай контекст и не используй приватные API для reconnect.
